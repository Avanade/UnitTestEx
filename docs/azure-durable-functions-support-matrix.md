# Azure Durable Functions testing support matrix

**Status:** Feasibility evidence only. This matrix describes what the current UnitTestEx APIs and isolated probes demonstrate; it is not a released orchestration-testing contract. There is no production UnitTestEx Durable orchestration runner or package today.

Use the [design record](./azure-durable-functions-design.md) for the spike history and decisions. Existing activity behavior is documented in [Azure Functions testing](./azure-functions.md).

## Status meanings

- **Supported today** means covered by an existing UnitTestEx API and its tests.
- **Experimental** means a test-only probe passed for the named scenario; it creates no supported product capability.
- **Not established** means untested or only partially tested. Do not infer support from SDK APIs, sample code, or a nearby passing probe.

## Type and capability matrix

| Durable Functions type or capability | What is demonstrated | What is not supported or remains unproven |
|---|---|---|
| **Activity functions — Supported today, direct invocation** | Existing `FunctionTester` can invoke real activity methods using `Trigger<T>()`. Tests cover static and instance methods, sync and async returns, DTO/collection inputs, DI, explicitly supplied `FunctionContext`, captured logs, and original activity exceptions. See [`DurableActivityTest`](../tests/UnitTestEx.NUnit.Test/DurableActivityTest.cs). | This does not start the Functions worker or Durable backend. It does not prove trigger indexing, binding conversion, runtime delivery, or Durable Task's activity-failure translation. |
| **Function-based orchestration methods — Experimental, SDK host** | The pinned in-memory host ran selected real methods, including static `ProcessBatch`, instance `FinalizeBatch`, and failure orchestration bodies, through public SDK delegate registration. Host-driven replay was observed. The non-packable prototype includes a fluent `FunctionTester.DurableTask()` facade that runs the real `RecoverWorkflow`, `DeclineWorkflow`, and `AwaitApproval` bodies, asserts completed output or nested failure details, exposes the raw SDK host, and emits the wall-clock timer diagnostic. See [`DurableTaskHostTest`](../tests/UnitTestEx.Azure.Functions.Durable.Test/DurableTaskHostTest.cs) and [`FluentDurableTaskTest`](../tests/UnitTestEx.Azure.Functions.Durable.Test/FluentDurableTaskTest.cs). The low-level `StartDurableTaskTestHostAsync` extension remains available for SDK registration shapes not yet covered by the fluent builder. | This is not Functions-worker orchestration support and does not invoke the worker, trigger pipeline, or Durable Functions extension input converters. The facade is experimental and non-packable; no production API exists. |
| **SDK class-based `TaskOrchestrator<TIn,TOut>` — Experimental, SDK host** | The pinned host registered and executed a typed `TaskOrchestrator<string,string>` through `DurableTaskRegistry.AddOrchestrator<T>()`; it scheduled an activity and returned the SDK host's output. A failing activity also produced nested `TaskFailedException` and `WorkflowRejectedException` failure details. See [`ClassBasedOrchestrationTest`](../tests/UnitTestEx.Azure.Functions.Durable.Test/ClassBasedOrchestrationTest.cs). | This is standalone Durable Task SDK behavior, not a class-based Azure Functions worker path. It does not establish DI-driven orchestrator construction or a reusable UnitTestEx arrangement API. |
| **Activity calls from an orchestration — Experimental, SDK host and method-level** | The host registered activity delegates and executed real activity methods. Probe delegates resolved the real activities from the FunctionTester's service provider, used scoped DI and captured logging, and supplied a `TestFunctionContext`. The controlled batch test verifies each item call receives the three-attempt, one-second initial retry policy; host tests observe both recovery after one failed attempt and parent failure after exactly three failed attempts. | The Functions worker is not running. Runtime retry evidence applies only to the pinned SDK host and this policy. The activity context is supplied by the test adapter, not worker middleware. |
| **Sub-orchestrations — Experimental, selected SDK-host scenarios** | `ProcessBatch` completed with the real `FinalizeBatch` child; a test child failure produced nested failure details. A separate SDK-host test verified a retrying child recovered on attempt three and an exhausted child produced failed parent metadata after three attempts, including the nested `WorkflowRejectedException` cause. A pending child also completed successfully or failed after its parent was terminated; neither outcome changed the parent's `Terminated` status. | General nested orchestration arrangements and a reusable UnitTestEx API are not established. The virtual-time context rejects child calls. |
| **Fan-out/fan-in — Experimental, selected scenarios** | The real batch body completed in the SDK host. A separate direct-context probe completed its three activity tasks in C/B/A order and verified the body returned results in input order. | The direct-context test controls task completion itself; it does not prove engine scheduling for all fan-out patterns. There is no general deterministic pump or public arrangement API. |
| **Durable timers — Experimental, two distinct behaviors** | The method-level context ran the real approval orchestration with a 24-hour timeout advanced instantly; boundary tests cover due timers, invalid deadlines/advances, multiple timers due in one advance, and a post-advance event that cannot change the timeout result. Host tests forwarded a test-only 100 ms timer, observed a real 100 ms approval timeout, and emitted the wall-clock warning. See [`ApprovalVirtualTimeTest`](../tests/UnitTestEx.Azure.Functions.Durable.Test/ApprovalVirtualTimeTest.cs), [`ApprovalHostEventTest`](../tests/UnitTestEx.Azure.Functions.Durable.Test/ApprovalHostEventTest.cs), and [`HostTimerDiagnosticTest`](../tests/UnitTestEx.Azure.Functions.Durable.Test/HostTimerDiagnosticTest.cs). | The context test does not use engine timer history or replay. `AdvanceBy` fires due timers before returning, so it cannot model an atomic same-deadline event/timer race; exact arbitration remains untested. The host has no virtual-clock control; its timer waits on real time. The short timeout is an explicit test input, not evidence about production-length timers. Do not silently shorten production delays. |
| **Configurable timeout values (`IOptions<T>` or equivalent) — Application design option, not a UnitTestEx feature** | The approval sample passes `Timeout` in serializable `ApprovalRequest` input. A host test explicitly supplied 100 ms and verified the real orchestration's timeout result; another kept the production-like 24-hour input and let an event win. | The sample does not use options injection, and no options override path is tested. A shorter explicit input tests a different timeout value; it does not advance virtual time or prove a production-duration host timer. Injecting `TimeProvider` controls only code that uses it; it does not control `TaskOrchestrationContext.CreateTimer`. Do not read mutable options inside replayed orchestration code if the value could change between episodes; prefer a stable input/versioned value. |
| **External events and timer/event coordination — Experimental, SDK host and method-level** | The host completed the real approval orchestration after an event while its 24-hour timer was pending; events sent before a wait was registered were buffered and deserialized, including two same-name events delivered to successive waits in arrival order. An event sent after completion left the completed output unchanged. The method-level context also tested event-before-timeout, timeout, pre-canceled waits, an event one tick before the deadline, and two same-named waits where one event completes the most recently registered wait. | Same-name waiter selection in the method-level context is helper-specific, not a Durable Task engine contract. These tests do not exercise Functions delivery or Functions serializer configuration. Exact same-deadline timer/event arbitration remains untested. |
| **Cancellation — Experimental, narrow cases** | The method-level context observed pre-canceled waits and cancellation after a timer/event wait was pending; a same-name event left the other wait pending for separate cancellation. In the host, a child remained `Running` after parent termination and completed or failed after its own event; a blocked activity delegate also finished after parent termination. | The pinned `TaskActivityContext` public API exposes no cancellation-token property, and general cancellation propagation is not established. These results do not imply that terminating an orchestration cancels its activities or children. |
| **Replay and determinism — Experimental, SDK host only** | The host replayed the tested batch orchestration; the timer diagnostic test also observed replay and emitted one warning rather than repeating it. [`ReplayDeterminismTest`](../tests/UnitTestEx.Azure.Functions.Durable.Test/ReplayDeterminismTest.cs) changes the activity name across replay and verifies a `NonDeterministicOrchestrationException` with both names in the diagnostic. | The virtual-time context always reports `IsReplaying == false`. The host did not promptly diagnose `Task.Delay`, `Task.Run` around durable work, or `ConfigureAwait(false)` in bounded probes; a watchdog timeout is not proof of permanent noncompletion. No universal invalid-await detector is available. See [`InvalidAwaitProbe`](../tests/UnitTestEx.DurableFunction.HostProbe/InvalidAwaitProbe.cs). |
| **Input/output serialization and failures — Experimental, standalone SDK** | DTO values crossed host boundaries. [`DurableSerializationTest`](../tests/UnitTestEx.Azure.Functions.Durable.Test/DurableSerializationTest.cs) round-tripped a nullable value, enum, and nested collection through an orchestration and activity. In `DurableTaskHostTest`, mutating caller input after scheduling did not change the orchestration input, and mutating a deserialized output did not affect a subsequent read. | The pinned host's documented options expose no serializer or `DataConverter` setting; generic service registration does not prove converter consumption. Functions extension serialization, custom serializer-option parity, and worker failure mapping remain unestablished. |
| **Custom status — Experimental, selected SDK-host scenario** | The real batch orchestration's `Finalizing` status was readable while it was waiting on its finalization child and again after completion. A separate orchestration updated status across two durable waits; each latest value was visible while running and the final value remained in terminal metadata. `SetCustomStatus(null)` cleared serialized status while running and after completion. | General status serialization/updates and Functions-worker behavior are not established. |
| **Entities, `ContinueAsNew`, durable HTTP, and custom retry handlers — Not established** | No end-to-end UnitTestEx support is demonstrated for these capabilities. The batch sample's activity retry policy is separately covered in the pinned SDK host. | Some are explicitly outside the initial scope; others appear in sample or SDK APIs without a corresponding runtime probe. The virtual-time context rejects entity access and `ContinueAsNew`; do not infer support from those methods existing in Durable Task. |
| **Starter/client/status operations — Not established as UnitTestEx features** | The SDK host's own client scheduled probe orchestrations and waited for their completion. | This does not test a Functions starter trigger, production `DurableTaskClient` behavior, status HTTP endpoints, or a UnitTestEx starter/status assertion API. |
| **Host lifecycle — Experimental, SDK host** | [`PendingOrchestrationDisposalTest`](../tests/UnitTestEx.Azure.Functions.Durable.Test/PendingOrchestrationDisposalTest.cs) disposed the host within a five-second bound with either an event wait pending or an activity delegate blocked. In the latter case disposal returned while the delegate remained blocked; the test then released it. [`OrchestrationTerminationTest`](../tests/UnitTestEx.Azure.Functions.Durable.Test/OrchestrationTerminationTest.cs) terminated a separate pending parent and observed terminal metadata. | This does not establish Functions-worker shutdown or Azure backend cleanup. Disposal does not wait for or cancel the probe's blocked delegate; activity/child cancellation propagation is not established. |
| **Functions worker, bindings, and backend integration — Not established by these probes** | Existing activity tests cover direct invocation only. A future real-host test belongs in a separate opt-in Aspire/integration project. | The SDK test host and method-level context do not prove Functions indexing, binding, worker startup, storage provider behavior, Azure authentication, or deployed backend behavior. |

## Dependency and framework boundary

All executable feasibility probes in this matrix were run on **.NET 10 only**. The provisional source projects under `src` target .NET 8, 9, 10, and 11, but are non-packable prototypes; only their net10 targets have been exercised. The host prototype pins `Microsoft.DurableTask.InProcessTestHost` **0.2.3-preview.1**; the method-level context helper pins `Microsoft.DurableTask.Abstractions` **1.28.0**. The published host package contains `net6.0`, `net8.0`, and `net10.0` assets; nearest-framework selection would use net8 assets for net9 and net10 assets for net11, but neither combination has been built or tested. Abstractions 1.28.0 provides a `netstandard2.0` asset. The current net10 restore resolves the shared Durable Task SDK packages to 1.28.0 and `Microsoft.Azure.DurableTask.Core` to 3.11.2. These asset/graph observations do not validate compatibility on other target frameworks or establish a production package guarantee.

The published host package is preview software. Its observed dependency graph and framework assets are recorded in the [design record](./azure-durable-functions-design.md). The optional `*.Durable.TestHost` prototype references `UnitTestEx.Azure.Functions` for FunctionTester integration; the dependency is one-way, so the existing Functions package does not acquire a Durable dependency.

## Reading this matrix

The three paths answer different questions:

1. **`FunctionTester` direct invocation** tests selected function-method behavior with the app's services, but does not start the Functions worker.
2. **The in-memory Durable Task host** tests selected SDK orchestration execution and replay, but does not provide virtual time or Functions-worker fidelity.
3. **The virtual-time context prototype** tests selected real orchestration-method coordination against a manually controlled context, but does not model durable history, replay, or Functions runtime behavior.

Only the first path is existing UnitTestEx behavior. The other two are experiments, not interchangeable implementations or release commitments.
